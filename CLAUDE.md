# Social Ops: in-house social media system

## What this is
An internal tool for our agency (Chania, Crete) to plan, create, approve and organize social media posts for **many client accounts**, faster.

**Organize mode (since 2026-11-04, D16):** the app organizes the work; the team posts in the apps by hand. Everything that posts through our drivers or reads back from the platform APIs (accounts and OAuth, publish queue, token monitor, preflight, reconcile, Withdraw, comment inbox, insights, monthly numbers, listening report) stays in the code but is off behind `FEATURE_PUBLISHING` (`config/features.php`, routes under `feature:publishing`, the scheduler, `@if (config('features.publishing'))` in the views). Tests run with the flag on (`phpunit.xml`) plus `OrganizeModeTest` for the off state. The sections below still describe the publishing features; read them as "when the flag is on". Clients are mostly hospitality: villas, hotels, beach bars/lounges, restaurants, local brands. Content is **Greek and English**.

Goal: cut time from every step: asset intake, captions, translation, approvals, scheduling, reporting.

## Core idea
Own the workflow and the publishing. No paid middleman.
- We build: client/brand profiles, asset inbox, content calendar, AI bilingual captions, client approval portal, reporting.
- We build the publishing too: our own Meta developer app (Instagram + Facebook via the Graph API), TikTok Content Posting API, each a driver behind a `Publisher` adapter interface (LinkedIn, added 2026-11-04 with D17, has no driver: planned and approved here, posted by hand). No paid aggregator (Panos's call, D2).
- Consequence: platform approvals (Meta App Review, TikTok audit) are the critical path. Start Phase 0 today. Build and test every driver in dev mode with the agency's own test accounts while approvals run; client publishing goes live per platform as each approval lands.

## MVP scope (Phase 1)
1. Client & brand profiles (accounts, voice, languages, pillars, hashtag bank, approval policy, approver contacts).
2. Asset inbox per client: no-login upload link, auto-naming, tags.
3. Content calendar with post state machine.
4. AI drafting: Claude API, EL + EN captions, per-platform variants, alt text, hashtags.
5. Client approval portal: signed expiring magic links, per-network previews, inline comments, approve on mobile, reminders.
6. Publishing to Instagram, Facebook and TikTok through our own drivers; LinkedIn by hand. TikTok posts stay private (SELF_ONLY) until the audit passes; until then public TikTok posts go through Manual-Needed. No other platforms, now or later.
7. Token health monitor, plus `posts:preflight` (hourly: every account with a post due in the next 24 hours answers one cheap API call, or Slack hears about it once a day).

Out of MVP: CSV import, evergreen queues, Canva autofill, auto-reports, auto-Reels. LinkedIn, YouTube, Threads, Pinterest and X are not planned.

## Post state machine
`Idea → Draft → In Review → Changes Requested → Approved (locked) → Scheduled → Published | Failed | Manual-Needed`, and `Published → Withdrawn` (the Withdraw button deletes the post through the Facebook API; Instagram and TikTok have none, so those stay listed on the post with a note until a human deletes them in the app).
- Approved posts are locked; editing one sends it back to In Review.
- Approval auto-schedules the post.
- A post with `settings.repeat` (weekly or monthly) spawns its next occurrence as a Draft right after it is published (`Post::spawnRepeat()`); the Draft goes through approval again.
- Code: `App\Posts\PostState` (enum with the transitions, `color()` for the badge classes; every page shows a state through `<x-state-badge :state>`, the calendar legend filters by state), `Post::transitionTo()`; captions live in `post_variants` per platform and language; `Post::captionFor()` builds the published text (languages, then the profile's `signatures.<platform>` line, then the hashtags).
- Numbers: `posts:insights` (daily) reads reach, views, likes, comments, shares and saves per platform into `posts.metrics` from Instagram, Facebook and TikTok (Display API, scope `video.list`).
- Manual-Needed covers things no API can do (Instagram Story stickers, shopping tags, public TikTok through our own app before its audit): notify a human to post in-app.

## Rules that must not be broken
- Never store client passwords. Official OAuth only.
- Never hard-code platform quotas. Read live limits (for example Instagram `content_publishing_limit`) before batch publishing.
- A human stays in the approval gate. AI drafts; it never publishes unapproved content.
- Greek captions get human review (gender agreement, idioms).
- Client data and media in EU-region storage. Log UGC repost permission and consent for people in assets.
- Each client is isolated: accounts, media, users, data.

## Dev setup
`composer install && cp .env.example .env && php artisan key:generate && php artisan migrate && npm install && npm run build`. The first staff login is created on `/setup` (only while there are no users) or with `php artisan staff:create "Name" email`; more logins on the Staff page (no public registration). A login can be limited to some clients there (`users.client_ids`, enforced by `App\Http\Middleware\LimitClients` on every staff page and in the lists): it sees only those clients and cannot manage logins. Run `php artisan test` and `vendor/bin/pint --test` before every commit; CI runs both. On the server, `/refresh` (the "Refresh after update" button, also on the dashboard) runs the migrations and `optimize` after a pull. Reminders and escalations need the scheduler (`php artisan schedule:work` locally, cron in production).

## Conventions
- Admins (`users.is_admin`: Panos's login by the migration, else the oldest login; the first login made on `/setup`; the Admin tick on the Staff page, admins only) get the Settings page (`/settings`, `SettingsController`, Gate `admin`): every variable of `.env` edited in the browser, written back in place (comments kept, the previous file as `.env.backup`), then `config:cache`; `APP_KEY` is locked.
- Asset/post naming: `CLIENT_YYYYMMDD_PLATFORM_FORMAT_PILLAR_LANG_v#`, e.g. `ALMYRA_20270512_IG_REEL_FOOD_EL-EN_v2`. Enforced automatically on upload; raw inbox uploads use `ANY` for the platform and `IMG`/`VID` for the format (e.g. `ALMYRA_20261103_ANY_IMG_FOOD_EL-EN_v1.jpg`) because platform and post format are decided later on the post.
- Link in bio: the public page `/bio/{slug}` (`App\Bio\BioLinks`: the profile placeholders that hold a link, a phone number or an e-mail, then the accounts) and, Panos's choice (D15), the same buttons on the client's own WordPress site: the box on the client form connects with a WordPress user and an application password (`accounts` row with platform `wordpress`, password encrypted, no expiry so the token monitor ignores it), `App\Bio\WordPress::publish()` creates the page `links` through the REST API once and overwrites it on every Publish, in the client's language; `resources/views/bio/fragment.blade.php` is both the public page body and the WordPress content.
- Clients board (`/clients`): one row per client with the agency's own fields from the profile's Agency tab (`clients.status`, `owner`, `priority`, `plan_due`, `posts_per_week`, `stories_per_week`, `tiktoks_per_month`, `pending`, `links`; `Client::STATUSES`, `Client::PRIORITIES`), the date the calendar is scheduled up to, this week's and the waiting-for-client counts; soonest plan due first, overdue in red. The client never sees these.
- Deadlines per client (`/clients/{id}/deadlines`, the Deadlines tab, `deadlines` table, `App\Models\Deadline`): what the agency owes and what the client owes for a month (title, side, due date, ticked when done), grouped by month; the tab counts and the dashboard lists the open ones due within 7 days (`Deadline::dueSoon()`), overdue in red.
- Instagram grid preview per client (`/clients/{id}/grid`): feed, carousel and Reel posts with a date, newest first, first asset as a thumbnail (`/assets/{id}/thumb`, `Asset::preview(600)`).
- Canva import (`App\Media\Canva`: the Connect API through our own integration, OAuth with PKCE, read-only scopes, keys in `services.canva`): the Canva box on the assets page connects the agency's Canva to the client (an `accounts` row with platform `canva`, refreshed on use, skipped by `accounts:check-tokens`), searches designs and queues `ImportCanvaDesign` per ticked design: PNG or JPG per page, or MP4, filed through `Client::storeAsset()` like an inbox upload (`uploaded_via` canva).
- Google Drive intake (`App\Media\GoogleDrive`: our own service account from `GOOGLE_SERVICE_ACCOUNT_JSON`, scope `drive.readonly`, JWT signed in PHP, token cached 50 minutes): the Google Drive box on the assets page checks a pasted folder link and keeps it as an `accounts` row with platform `drive` (`external_id` = folder id, empty token, no expiry so the token monitor ignores it); `inbox:pull` (hourly) queues `PullDriveFolder` per folder, which files every photo and video the inbox has not seen yet (`assets.source_id` = `drive:<file id>`) through `Client::storeAsset()` with `uploaded_via` drive. Subfolders are not read, one folder per client.
- Folder intake (the Google Drive and Dropbox boxes on the assets page): `App\Media\GoogleDrive` is our own service account (`GOOGLE_SERVICE_ACCOUNT_JSON`, scope `drive.readonly`, JWT signed in PHP, token cached 50 minutes), a pasted folder link is checked and kept as an `accounts` row with platform `drive` (`external_id` = folder id, empty token); `App\Media\Dropbox` is our own Dropbox app (OAuth with PKCE, `DROPBOX_APP_KEY` only, the agency's account, tokens refreshed on use and ignored by the token monitor like Canva), the folder path lives in the row's `meta.folder`. `inbox:pull` (hourly) queues `PullFolder` per watched folder, which files every photo and video the inbox has not seen yet (`assets.source_id` = `<platform>:<file id>`) through `Client::storeAsset()` with `uploaded_via` drive or dropbox. Subfolders are not read, one folder per client and source.
- Reels from clips (`App\Media\ReelAssembler`, ffmpeg from `FFMPEG_PATH`, Symfony Process): the "Make a Reel" box on the assets page takes 2 to 10 ticked video assets (file-name order), seconds per clip, an optional headline (drawtext over the first 3 seconds, wrapped with `TextOverlay::wrap()`) and a pillar; `AssembleReel` (queued) scales and crops each clip to 1080×1920, concatenates them without sound (music is added in the app) and files the MP4 through `Client::storeAsset()` with `uploaded_via` reel. No ffmpeg on the server: the box says so.
- Client brand profiles live in the `clients` table (`profile` JSON column in the `example.yaml` shape, `Client::toProfileArray()` returns the full shape). The client form edits every section as plain fields in five tabs (Basics, Voice and content, Approval and timing, Research, Replies and webhooks: Alpine `x-show`, one form, the open tab remembered in the browser; `ClientProfile::fromForm()` builds the profile from the `p[...]` inputs; no YAML in the interface; the link name and the code are made from the name when left empty). `notes` is free-text extra information about the client, given to Claude in the caption, rewrite, plan, reply and trend prompts as `{{notes}}`. `config/clients/<slug>.yaml` files are imported with `php artisan clients:import`; `example.yaml` stays the template. Every client-owned table carries `client_id`.
- Placeholders: the profile's `fields` map (`{{phone}}`, `{{site}}`, `{{booking}}`, any lowercase name) is filled by `Client::substitute()` in captions, signatures and the first comment at publish time, in the approval preview, the live counter, the ZIP and the CSV; an unknown placeholder fails the publish instead of going out as written.
- Posts the client published themselves in the Instagram or Facebook app: the "Import last 30 days" button on the accounts page (`App\Posts\PostImporter`) pulls them in as Published posts with their external id, so the calendar, the insights and the monthly report see them; running it again imports only what is new.
- Clients connect their own accounts through the signed "connect link" on the accounts page (`/connect/{slug}`, 7 days): same OAuth flow and pick step as staff, in the guest layout, `connected_by` empty. The OAuth callback and the pick step are outside the auth group on purpose: the state and candidates in the session are the credential.
- View-only client calendar: signed link from the staff calendar (client selected), `/calendar/{slug}`, 30 days, this month and the next, states in client words (`CalendarController::CLIENT_STATES`).
- Caption prompt: `prompts/caption-draft.md`. Shortening prompt: `prompts/shorten-caption.md` (`App\Drafting\CaptionShortener`, the "Shorten with Claude" button next to each platform's live character count on the post form). Rewrite prompt: `prompts/rewrite-caption.md` (`App\Drafting\CaptionEditor`, the "Change with Claude" box above the captions: an instruction rewrites every ticked platform and language at once, `POST /posts/{id}/rewrite`, unsaved until Save). Comment reply prompt: `prompts/comment-reply.md` (comment inbox per client, `php artisan comments:fetch` hourly: Instagram and Facebook comments, Instagram and Facebook direct messages of the last 30 days (same `comments` table with a `thread_id`, the sender's id the reply goes to through `MetaPublisher::message()`, within Meta's 24-hour window; scopes `instagram_manage_messages` and `pages_messaging`)). Triage prompt: `prompts/comment-triage.md` (`App\Engagement\CommentTriage` tags each new comment with a sentiment and an intent at fetch time; `Comment::needsAttention()` sorts the inbox and counts into the Slack line; `saved_replies` in the profile are offered next to the reply box).
- Instagram collab posts: `settings.instagram.collaborators` on the post form (up to 3 usernames, feed, carousel and Reel) goes on the media container as `collaborators`; the invited accounts accept in the app. Not for Stories.
- Team notes on a post (`post_notes`, `PostNote`, the box under the post form, also on published posts): internal only; `@FirstName` in a note pings that colleague on Slack with a link (`PostNote::mentioned()`).
- Listening report prompt: `prompts/listening-report.md` (`App\Reporting\ListeningReport`, weekly `listening:report`: the profile's `research.hashtags_to_watch` through the Instagram Hashtag Search API, `research.competitors` through Business Discovery, both via the client's connected Instagram account; no scraping, ever).
- Keyword auto-replies: a `saved_replies` entry with `keywords` answers a new Instagram or Facebook comment that contains one of them at fetch time (`FetchComments::autoReply()`, the saved text as written by a human, marked replied); comments the triage flagged (question, complaint, negative) or could not tag wait for a human, Google reviews always do.
- Monthly report prompt: `prompts/monthly-report.md` (`App\Reporting\MonthlyReport`: numbers built in PHP from `posts.metrics`, read back daily by `posts:insights`; Claude writes the reading).
- Holidays (`App\Planning\Holidays`, no table): Greek holidays and name days, Cretan anniversaries, Cyprus's own when the client's location says Cyprus, the holidays of the guests' countries (labelled by country code), the international awareness and celebration days, and the awareness months on their first day ("all month"); Orthodox and Western Easter computed. Amber lines on the calendar (`CalendarController` splits the " · " of a shared date into lines) and the `{{holidays}}` lines of the planning prompt (`Holidays::lines()`). Greek names for the Greek days and the big world days, English for the rest.
- Pillar mix: `App\Planning\PillarMix::for($client)` counts the posts per pillar 30 days back and ahead (not Failed or Withdrawn, with a pillar) against the profile's shares; a pillar 15 points or more off target with at least 5 posts in the window is "drifted": red on the client form's pillar strip, a "Pillar mix off target" box on the dashboard, and a Slack line from the Thursday `slots:check`.
- Best times: `App\Planning\BestTimes::for($client)` ranks the weekday-and-hour slots of the client's Published posts of the last 90 days by average interactions (likes, comments, shares and saves over every platform, from `posts.metrics`), at least 3 posts per slot, top 3: the "Best time from our numbers" button on the post form fills the next occurrence of the best slot, and the client form shows the list under the weekly slots.
- UTM: `utm: true` in the profile makes `Client::tagLinks()` add `utm_source=<platform>&utm_medium=social&utm_campaign=<post name>` to every link in captions, first comments at publish time; links that already carry `utm_` are left alone.
- Trend brief and batch plan prompts: `prompts/trend-research.md`, `prompts/content-plan.md`. `php artisan content:plan <client> --posts=N` drafts a reviewable batch; `--brief <file>` skips the web research and uses a pasted brief instead; `--latest-brief` reuses the client's trend brief of the last 7 days (`reports` row, kind `trend_brief`); `--instruction "…"` makes the planner follow the team's words instead of the pillar quota. The "Plan with Claude" form on the client page runs the same command as a queued job (`App\Jobs\PlanContentBatch`) and mails the outcome; the "Post from a prompt" box above it runs it for one post (`--posts=1 --instruction --latest-brief`, `POST /clients/{id}/draft`) and the mail carries the post link.
- Monthly report to the client: "Email to client" on the report page, or `approval.email_monthly_report: true` for the job to do it, mails the approvers a signed 30-day link (`/reports/{id}/client`, guest layout) with the month's numbers attached as CSV (`MonthlyReport::mail()`, `MonthlyReport::csv()`).
- JSON API and webhooks (`docs/api.md`): bearer tokens from the Staff page (`api_tokens`, hashed, optionally limited to one client, `App\Http\Middleware\ApiAuth`), `routes/api.php` reads clients, posts and the inbox, creates Drafts through the same `PostRequest` as the form and answers comments; it never publishes. The profile's `webhooks` list gets a signed JSON POST (`App\Webhooks\Webhooks`, `SendWebhook` job, `X-SocialOps-Signature` HMAC) on `post.published`, `post.failed`, `post.manual_needed`.
- Greek by default: `config('app.locale')` is `el` unless `APP_LOCALE` says otherwise (tests run in English, `phpunit.xml`). The plan Claude writes (titles, angles, why now, briefs, the trend brief: `{{plan_language}}` in the planning prompts, from `PlanRequest::promptVars()`), the review sheet, the report titles and the Word export follow the client's first profile language; captions keep their own languages.
- Dates shown to people are DD-MM-YYYY (`format('d-m-Y')`, a weekday name or a time around it where there was one; Panos, 2026-11-05); month headings keep the month name, the Word export keeps its own `d/m`, and machine values (input values, URLs, keys, CSV, API, post names) stay ISO. The calendar's From–To range draws one titled grid per month.
- Interface languages: English and Greek. `lang/el.json` has one entry per `__()` string (`tests/Feature/LocaleTest.php` fails when one is missing or its placeholders differ); `lang/el/` holds the validation and login messages. `App\Http\Middleware\SetLocale` picks the login's `users.locale` (the switch in the user menu, `POST /locale`), else the choice made in that browser, else on client pages the client's first profile language (`Client::uiLocale()`). Mails to approvers go out in the client's language, mails to staff in theirs. Dates with day or month names use `translatedFormat`.
- MCP server (`routes/ai.php`, `App\Mcp\SocialOpsServer`, laravel/mcp): `/mcp` over HTTP with the same bearer tokens and scope as the API, or with the OAuth login claude.ai's custom connector uses (Laravel Passport, `Mcp::oauthRoutes()`, `App\Http\Middleware\McpAuth`, the Allow page `auth/oauth-authorize`, redirect domains in `config/mcp.php`; the tools then see the login's clients; `/refresh` makes the Passport keys once), `php artisan mcp:start socialops` over stdio. Tools list-clients, list-posts, get-post, create-draft and update-post (the same `PostRequest` as the form; update-post changes only the fields sent and reopens an approved post for review), get-caption-brief (the caption prompt filled for a post; Claude writes and files with update-post: the connector's version of the Draft, Shorten and Change buttons), list-claude-jobs (the queue: posts ticked "Ask Claude for the captions" = `settings.ask_claude`, plan requests from the client page = `reports` rows of kind `claude_job`; cleared by update-post with `ask_claude` false and save-plan with `job`; an hourly scheduled task on the agency's Claude plan, made from the project chat, runs them), get-planning-brief and save-plan (D18, the planning recipe in `docs/api.md`: the brief with the profile, quota, window, holidays, recent topics and the content-plan prompt; Claude in the chat researches the trends and plans; `save-plan` files the Drafts, the trend brief and the plan review sheet through `App\Planning\PlanWriter`, which `content:plan` shares), and while publishing is on list-comments, reply-to-comment (`Comment::answer()`), month-numbers (`MonthlyReport::numbers()`) (`SocialOpsServer::boot()` drops them otherwise); same shapes as the API, never publishes.
- Word export of the θεματολογία (topic plan): "Download Word" on a plan report (`/reports/{id}/word`, `App\Reporting\TopicsDocx`, plain WordprocessingML in a zip, no library) writes the plan in `reports.meta` for the client in the client's language, in the layout of the team's hand-written files: title, one bold line and the angle per post, a shaded box with why now, assets, caption brief and pillar. `save-plan` answers with the link.
- Claude from the server is behind `FEATURE_CLAUDE_API` (`config/features.php`, routes under `feature:claude_api`, `@if (config('features.claude_api'))` in the views; off since D18): the "Plan with Claude", "Post from a prompt", "Draft captions", "Shorten" and "Change with Claude" buttons. With the flag off the client page shows the MCP-mode "Plan with Claude" box instead: the fields build the request to paste to Claude. The `content:plan` command still works on the server for anyone with a key.
